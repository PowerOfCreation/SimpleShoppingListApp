# Sync: wichtige Entscheidungen

Dieses Dokument hält fest, *warum* etwas so ist, wie es ist (rückblickend). *Was gelten soll*, steht in [`sync-sharing-target.md`](./sync-sharing-target.md) — bei Widerspruch ist das dort maßgeblich.

Kurzreferenz zu den nicht-offensichtlichen Entscheidungen aus der Listen-Sync-Implementierung (`api/sync/`, `database/outbox-repository.ts`, `backend/internal/application/services/event-ingestor.go`, `backend/internal/infrastructure/realtime/`).

Sync ist inzwischen bidirektional: Push (Client → Server, seit Anfang an) **und** Pull (Server → Client, inklusive Listeninhalt — nicht mehr nur der Listenkopf). Ein eigener Abschnitt dazu folgt unten; die ursprünglichen Push-only-Entscheidungen darunter gelten weiterhin.

## Client-ID vs. Keycloak-Identität

**`client_id`** (`api/common/client-id.ts`) ist **keine** separat erzeugte, persistierte Geräte-ID mehr. Eine frühere Version schrieb beim allerersten App-Start eine Zufalls-UUID nach `app_preferences`; das ist entfernt. Stattdessen liefert `getClientId()`:

- die **Keycloak-`sub`** (via `getCurrentUserId()` in `api/auth/auth-service.ts`, ein synchroner Cache der bei `login`/`restoreSession`/`logout` gepflegt wird), sobald ein Nutzer angemeldet ist;
- sonst den **`Device.deviceName`** (`expo-device`, Fallback `"unknown-device"`), rein für Lesbarkeit im lokalen Event-Log.

Zweck: (1) WebSocket-Ack-Routing (Server muss wissen, an welche Verbindung ein Ack geht), (2) Attribution auf `domain_events.client_id` ("wer hat das erzeugt").

**Warum zusammenlegen:** Sync läuft nur, wenn angemeldet (SyncProvider gated auf `signedIn`). In dem Moment, wo die ID überhaupt über eine lokale Attribution hinaus gebraucht wird, existiert immer eine Keycloak-`sub` — eine parallel generierte Zufalls-ID wäre überflüssiger Mechanismus. Dass mehrere Geräte desselben Accounts denselben Routing-Key teilen, ist harmlos (ein Ack für ein Event, das ein Gerät nicht in seiner Outbox hat, ist beim `markSynced` ein No-Op) und ist genau das, was ein künftiges "andere Geräte benachrichtigen"-Feature will. Zusätzlich ist die `sub` eine echte Identität statt einer unbeaufsichtigten Self-Declared-String (die alte `?client_id=` im Query-Param war komplett ungeprüft; später wird der Server das aus dem verifizierten Token statt aus dem Query-Param lesen).

**Zur eigentlichen Frage — App löschen + gleicher Keycloak-Account:** Das lässt sich mit client_id nach wie vor nicht lösen, und der inzwischen gebaute Pull-Sync (siehe unten) löst es bewusst auch nicht: Pull läuft nur für Listen, die lokal **bereits bekannt** und sync-aktiv sind (per Entscheidung — kein serverseitiges "gib mir alle Listen dieses Accounts", das bräuchte User-Scoping, das es noch nicht gibt). Bei einer Neuinstallation ist die lokale SQLite-DB komplett leer, also auch keine sync-aktive Liste bekannt, also nichts zum Pullen. Eine echte "stelle meine Listen nach Neuinstallation wieder her"-Funktion ist explizit ein separates, größeres Feature.

**Dein Instinkt zu "keine Migration nötig" ist trotzdem genau richtig** — nur für das spätere User-Scoping-Feature, nicht für client_id. Wenn Nutzer-Zuordnung kommt: **kein** `user_id`-Feld lokal in SQLite, keine Migration. Der Server liest die Nutzer-Identität aus dem verifizierten JWT der eingehenden Sync-Anfrage und setzt `user_id` beim Insert von `todo_lists`/`events` selbst — nie vom Client mitgeliefert (sonst könnte man sich als anderer Nutzer ausgeben). Das passt exakt zu deiner Idee "wird automatisch die eigene ID gesetzt", nur dass das serverseitig beim Empfangen passiert, nicht clientseitig beim Laden aus der lokalen DB.

## Weitere Kernentscheidungen (kurz)

- **Kein persistierter "sent"-Zustand** in der Outbox — nur `pending`/`synced`. Ein "sent" ohne Ack hätte keinen Weg zurück. In-Flight wird nur im Speicher gehalten (App-Neustart macht alles wieder `pending`, harmlos dank `ON CONFLICT DO NOTHING`/Upsert serverseitig).
- **Ack-Modell:** 202 = "angenommen", **nicht** committed. Erst ein WebSocket-Ack (nach echtem DB-Write) markiert `synced`. Reconcile (`/api/v1/sync/state`) ist die Ausfallsicherung, wenn ein Ack verloren geht.
- **Backend-Reihenfolge:** Ein einziger Worker verarbeitet alle Events strikt FIFO (statt Upsert-Semantik in den Domain-Handlern). Dadurch kann pro Aggregat nichts in falscher Reihenfolge verarbeitet werden, ohne die geteilte `ToDoListService`-Logik anzufassen, die auch die normalen REST-Endpunkte nutzt.
- **WebSocket-Hub:** Verbindungen werden über Zeiger-Identität abgemeldet, nicht über die client_id als Schlüssel direkt — verhindert, dass ein Reconnect durch die verspätete Cleanup-Routine der alten (toten) Verbindung wieder gelöscht wird.
- **Sync-Toggle nur nutzbar wenn angemeldet** — abgemeldet ist der Schalter sichtbar, aber deaktiviert. Kein Zustand, den die App nicht einlösen kann.
- **Backend-URL** kommt aus `.env.development`/`.env.production` (nicht `Constants.expoConfig.extra`), weil das zur Bundle-Zeit fest verdrahtet wird und nicht davon abhängt, welcher Prozess gerade `app.config.js` ausgewertet hat.
- **JWT-Prüfung ist Pflicht, User-Scoping nicht.** Das Backend verifiziert Bearer-Token gegen das gehostete Keycloak (`internal/interface/api/middleware`, Signatur via JWKS + `iss` + `exp`; `aud` ist bei Keycloak-Access-Token immer `"account"`, deshalb wird stattdessen `azp` gegen die erwartete Client-ID geprüft). Fehlt `KEYCLOAK_ISSUER`/`KEYCLOAK_CLIENT_ID` oder ist der Issuer nicht erreichbar, startet der Server gar nicht — kein Passthrough-Fallback, keine hybride Lösung. Die Test-Suite ist davon unabhängig: Controller-Tests reichen dort `middleware.Passthrough` explizit ein statt über `NewKeycloakAuth` zu laufen. Was weiterhin fehlt: **User-Scoping der Daten.** Jeder gültige Token (irgendeines Accounts) darf noch jede bekannte Listen-UUID lesen/schreiben — die Middleware schließt "API ist komplett offen", nicht "Nutzer A sieht Nutzer Bs Listen". Muss vor Produktivbetrieb mit echten Nutzerdaten nachgezogen werden.
- Die alten `/api/v1/todo-lists`-CRUD-Routen aus der Prä-Sync-Zeit liefen
  ohne `authMW` — echter Passthrough, nicht bloß fehlendes Scoping. Ersatzlos
  entfernt (kein Frontend-Aufrufer), damit "kein Passthrough" oben für die
  gesamte API stimmt.

## Pull-Sync: Listeninhalte, nicht mehr nur der Listenkopf

Kernentscheidungen aus der Erweiterung auf bidirektionalen Sync (`api/sync/sync-engine.ts`, `api/sync/event-applier.ts`, `database/sync-cursor-repository.ts`, `backend/migrations/00004-*`, `backend/internal/interface/api/rest/sync-pull-controller.go`).

- **`seq` wird beim `MarkProcessed` vergeben, nicht beim Insert.** Ein `BIGSERIAL` beim Insert hätte eine Sichtbarkeitslücke: Sequenzwerte werden beim `INSERT` gezogen, aber erst beim `COMMIT` sichtbar, zwei nebenläufige Inserts können also außer der Reihe committen. Ein Client, der `seq=5` sieht während `seq=4` noch uncommitted ist, verliert Event 4 dauerhaft. `MarkProcessed` läuft dagegen ausschließlich im einzigen Worker-Goroutine des `EventIngestor`, strikt FIFO, als eigenes Autocommit-Statement — Vergabereihenfolge ist damit Commit-Reihenfolge ist Sichtbarkeitsreihenfolge. **Gilt nur bei genau einem Ingestor-Writer**; mehrere API-Replicas brauchen entweder eine Leader-Election um den Ingestor oder eine Pull-Watermark unterhalb jeder in-flight `seq`.
- **`list_id` ist ein eigenes, vom Client gesetztes Feld** (nicht aus dem Payload gefiltert, nicht `aggregate_id`). Ingredient-Events haben `aggregate_id = ingredientId`; ohne `list_id` bräuchte jeder Pull/Reconcile-Call eine Aufzählung aller Ingredient-IDs statt einer einzigen Listen-ID. Rückwirkend befüllt in `migration-5.ts` (Frontend) bzw. `00004-events-list-id-and-seq.up.sql` (Backend), aus dem `ingredient.created`-Payload bzw. per Self-Join.
- **Gepullte Events werden per Scoped-Rebuild angewendet, nicht inkrementell.** Ein einzelnes gepulltes Event gegen den aktuellen Stand zu patchen ist mit den bestehenden Projektions-Handlern nachweislich falsch: kein Ordnungs-Guard (ein älteres Remote-Update kann ein neueres lokales überschreiben), lokal gelöschte Items können durch ein verspätetes `ingredient.created` wiederauferstehen, ein doppeltes `INSERT` wirft. Stattdessen fügt `EventApplier` die neuen Zeilen ein und baut danach die Projektion der betroffenen Liste komplett aus der **gemergten** (lokal + gepullt) Historie neu auf.
- **Konfliktauflösung ist Rebase, nicht Last-Writer-Wins nach Wanduhr.** `domain_events.seq` ist die Position, die der Server beim `MarkProcessed` vergeben hat; solange ein lokal erzeugtes Event noch nicht gepusht+geackt ist, ist sein `seq` `NULL`. Replay-Reihenfolge (`byServerSeqThenLocal`, `types/DomainEvent.ts`) ist: erst alle Events mit `seq` aufsteigend (der bestätigte, server-autoritative Prefix), danach die eigenen noch unbestätigten Events in lokaler Einfüge-Reihenfolge (`rowid`) — exakt wie `git rebase`: `origin/main` plus lokale Commits obendrauf. `occurred_at` ist reines Anzeige-Metadatum, keine Ordnungsgrundlage mehr — Uhrenversatz zwischen Geräten kann also keine Kausalität mehr verfälschen. Der bewusst in Kauf genommene Preis: ein Gerät, das lange offline war, landet mit seinen Events hinter allem, was der Server zwischenzeitlich von anderen Geräten bekommen hat, obwohl sie chronologisch früher entstanden — und der lokale optimistische Zustand kann beim nächsten Ack/Pull sichtbar auf die Server-Reihenfolge umspringen. Echte kausale Ordnung bräuchte Vektoruhren; für diese App-Klasse ("wer zuletzt ankommt, gewinnt") nicht gerechtfertigt.
- **Genau ein Writer für `seq`: der Pull-Pfad.** Ursprünglich trug der Ack `seq` mit, und `SyncEngine.handleAck` schrieb es direkt auf die lokale Zeile (`EventRepository.markSeq`) und baute die betroffene Liste neu auf (`EventApplier.rebuildForAck`) — das Event wanderte dabei vom unbestätigten Tail in den bestätigten Prefix, was die Replay-Reihenfolge verschieben konnte. Das hatte zwei Konsequenzen, die sich als struktureller Fehler herausstellten: `seq IS NULL` war mehrdeutig ("noch nicht gesendet" vs. "Server hat es bereits verarbeitet, aber wir haben den Ack verpasst" — ein zweiter Ack kommt nicht von selbst, sondern erst, wenn der nächste Flush das Event erneut sendet und der Ingestor es als alreadyProcessed nochmal ackt), und jeder Ack löste potenziell einen Rebuild aus, dessen Ergebnis von der *Verarbeitungsreihenfolge* zweier nebenläufiger, unabhängig dispatchter Acks abhing (`SyncSocket.handleMessage` ruft `onAck` synchron und unawaited auf) — nicht notwendigerweise ihrer Ankunftsreihenfolge. In der Praxis führte das dazu, dass ein Rebuild gelegentlich `todo_list.sync_enabled` vor `todo_list.created` einsortierte und die Sync-Einstellung einer Liste dauerhaft zurücksetzte. Jetzt schreibt ausschließlich `EventRepository.insertRemote` (Pull-Pfad) `seq`, atomar mit dem Cursor-Vorschub (`EventApplier.apply`). `handleAck` markiert nur noch die Outbox-Zeile als synced — sonst nichts. Damit ist `seq IS NULL` wieder eindeutig ("noch nicht im gesehenen Server-Prefix"), ein verlorener Ack ist folgenlos (der nächste Pull vergibt das `seq` ohnehin), und die Verarbeitungsreihenfolge zweier Acks ist irrelevant, weil ein Ack die Replay-Reihenfolge gar nicht mehr beeinflussen kann.
- **WebSocket-Fan-out ist Subscription-basiert** (`{"type":"subscribe","list_ids":[...]}`), nicht Broadcast-an-alle-Client-filtert und nicht `client_id`-geschlüsselt. Broadcast würde jede Listen-UUID an jede verbundene Verbindung leaken; `client_id`-Schlüsselung funktioniert nur für "meine eigenen anderen Geräte" und kann geteilte Listen (späteres Feature) strukturell nicht abbilden. Subscription verschärft die Sicherheitslage nicht: Abonnieren setzt Kenntnis der UUID voraus, und die reicht heute ohnehin zum Lesen über `/sync/events`.
- **Echo wird nicht über `client_id` unterdrückt.** Das würde die anderen Geräte desselben Nutzers stummschalten — genau der Fall, der die Notification eigentlich bedienen soll. Stattdessen: Apply ist idempotent (No-op bei bereits bekannten Events), Pull-Trigger werden 400ms debounced, und ein Pull wird übersprungen wenn `seq <= last_seen_seq`.
- **Neue Lese-Exposure durch `GET /api/v1/sync/events`.** Bis zur Pull-Arbeit war die API praktisch nur schreibend; jetzt kann ein gültiger Token die komplette Event-Historie einer bekannten Listen-UUID lesen. Die JWT-Middleware (siehe oben) verhindert anonymen Zugriff, aber **nicht** Zugriff durch einen fremden angemeldeten Nutzer auf eine erratene/bekannte fremde Listen-UUID — dieselbe User-Scoping-Lücke wie beim Schreiben, jetzt auch beim Lesen relevant.
- **`sync_cursors` ist eine eigene Tabelle**, keine Spalte auf `ingredient_lists` — die Projektion wird bei jedem Rebuild komplett neu aufgebaut (`DELETE FROM ingredient_lists` zuerst), ein Cursor dort würde bei jedem Rebuild still auf 0 zurückfallen und einen Voll-Pull erzwingen.
- **Ob *dieses Gerät* eine Liste synct, ist eine eigene Tabelle (`list_sync_settings`), keine Spalte auf `ingredient_lists` und kein Domain-Event.** Ursprünglich war das ein Event-Paar (`todo_list.sync_enabled`/`sync_disabled`), das in die Projektion einging — mit genau der Schwäche, vor der der vorige Punkt bei `sync_cursors` bereits warnt: ein `DELETE FROM ingredient_lists` vor jedem Rebuild setzt eine dort mitgeführte Einstellung bei jedem Rebuild auf ihren Default zurück. In der Praxis führte das zu einem sich selbst verstärkenden Defekt: eine Race zwischen zwei WebSocket-Acks (siehe „Genau ein Writer für seq" unten) konnte einen Rebuild auslösen, der `todo_list.sync_enabled` vor `todo_list.created` einsortierte, das `UPDATE` no-opte und `created`s `INSERT` den Wert stumm zurücksetzte. Schlimmer: welche Listen überhaupt gepullt/reconciled/subscribed werden, hing an genau diesem Wert — eine einmal falsch zurückgesetzte Liste war damit dauerhaft aus dem einzigen Mechanismus ausgeschlossen, der sie hätte reparieren können (Catch-22). Die Lösung ist strukturell, nicht ein weiterer Sonderfall in der Rebuild-Logik: ob dieses Gerät synct, ist eine reine Geräteentscheidung, gehört nicht in eine aus dem (servergemergten) Event-Log abgeleitete Projektion und wird nie mehr rebuildet, gepusht oder gepullt. `todo_list.sync_enabled`/`sync_disabled` als Event-Typen existieren nur noch historisch (alte Zeilen in `domain_events`, aus denen `migration-7` `list_sync_settings` einmalig befüllt).
- **`todo_lists` (Backend) ist eine abgeleitete Projektion, keine Autorität.** `UpdateToDoList`/`DeleteToDoList` machen kein `FindById`-dann-Fehler mehr, sondern sind No-ops bzw. idempotente Tombstone-Upserts auf einer fehlenden oder bereits gelöschten Zeile (`sql/queries/todo-lists.sql`) — "Zeile fehlt" ist in einer Projektion nie ein Fehler, aber `deleted_at` ist terminal, ein wiedereingereihtes `created` (z. B. durch `sweepUnprocessed`) darf eine gelöschte Liste nie auferstehen lassen. `created_at`/`updated_at`/`deleted_at` stammen dabei aus `occurred_at` des jeweiligen Events (durch `EventDispatcher.Dispatch`/`EventHandler.Handle` gereicht, nicht neu aus der Server-Uhr oder dem Payload hergeleitet) — genau wie oben bei der Konfliktauflösung ist `occurred_at` damit reines, clientgeliefertes Anzeige-Metadatum, nie Grundlage für Ordnung, Autorisierung oder Retention. `updated_at` kann dadurch rückwärts laufen: Replay ordnet nach `seq`, nicht nach `occurred_at`. `ToDoListService.RebuildList` baut die Projektion einer Liste aus ihrer Event-Historie neu auf (dieselben Handler, eine Transaktion) — Grundlage für den späteren Unsync-Endpunkt, an keine Route gehängt.
- **`SyncEngine.flush()` drained die Outbox seitenweise über `getPending`s Keyset-Pagination**, nicht per naivem `while (pending.length > 0)`: Zeilen verlassen `pending` nie als Nebeneffekt des Sendens, sondern nur über Ack/Reconcile — der Keyset-Cursor (nicht der Zeilenstatus) ist also der einzige Fortschrittsbeweis, den die Schleife hat. `MAX_DRAIN_BATCHES` (20 Batches × 50 Events) ist ein Sicherheitsventil, damit ein ungewöhnlich großer Rückstand (z. B. Stunden offline mit aktivem Sync) nicht einen einzelnen `flush()`-Aufruf blockiert und den Rest der App aushungert — der nächste Trigger (Outbox-Änderung, Vordergrund, Safety-Interval, Ack) macht dort weiter, wo dieser aufgehört hat.
- **Reparatur: voller Re-Pull.** `reconcile` prüft seit „Genau ein Writer für seq" beide Richtungen: fehlt dem Server ein lokales Event, wird es neu eingereiht (bestehendes Verhalten); kennt der Server umgekehrt ein Event, das lokal noch `seq === null` zeigt, ist das unter der Ein-Writer-Invariante kein „noch nicht gesendet" mehr, sondern ein Zeichen, dass die lokale Reihenfolge dieser Liste vom Server abweicht (z. B. eine Pull-Seite, die unter mehreren Backend-Replicas ohne Leader-Election ein Event übersprungen hat — siehe die Einschränkung zu `MarkProcessed` oben). Ein normaler inkrementeller Pull kann das nicht selbst erkennen, weil er dem lokalen Cursor vertraut und ein Event hinter ihm nie erneut anfasst. `SyncEngine.repairList(listId)` ist der Ausweg: Cursor auf 0, kompletter Neu-Pull. `insertRemote` füllt dabei jedes lokal noch unbestätigte `seq` nach, und der anschließende Rebuild leitet die Projektion aus der vollständigen, korrekt geordneten Historie neu ab — kein neuer Endpunkt, keine Backend-Änderung. `reconcile` löst das automatisch aus; zusätzlich gibt es „Re-sync from server" im Kontextmenü (nur sichtbar bei aktivem Sync) für den manuellen Fall. Als Diagnose-Netz protokolliert `IngredientListProjection.rebuildForList` eine Warnung, wenn eine Liste Events, aber kein `todo_list.created` in der gemergten Historie hat — der Fall, in dem die Liste sonst kommentarlos unsichtbar bliebe, bis eine Reparatur läuft; `handleCreated` ist dafür ein Upsert statt eines reinen `INSERT`, damit ein solches Rebuild nicht selbst an einem doppelten/echoten `created`-Event scheitert. Der Drift-Check greift dabei erst, wenn unser lokaler Cursor den Server-Head bereits erreicht hat: davor ist `seq === null` bei einem server-bekannten Event der Normalzustand jedes gerade gepushten und geackten Events bis zum nächsten Pull, kein Drift-Signal. `SyncCoordinator` awaitet deshalb `pullNow()` vor `reconcileNow()` (statt beide nebenläufig zu starten) — sonst träfe ein parallel laufender Reconcile regelmäßig genau diesen Zustand und würde per `repairList` einen unnötigen, mit dem laufenden Pull um den Cursor konkurrierenden Voll-Re-Pull auslösen.

## Listen teilen: Invite-Links

Kernentscheidungen aus dem List-Sharing-Feature (`backend/internal/domain/entities/{invite-token,invite-ttl,list-invite,list-member}.go`, `backend/internal/application/services/list-sharing-service.go`, `backend/internal/interface/api/rest/list-sharing-controller.go`). Freunde/Direkteinladung sind explizit **nicht** Teil dieses Features — nur mehrfach nutzbare Links.

Zielarchitektur (Rollen): nur der `owner` darf Sync einschalten und teilen (Einladen/Einladungen einsehen/widerrufen), und nur solange die Liste sync-aktiv ist; jeder eingeladene `member` darf die Liste sehen/bearbeiten, aber nicht selbst einladen und hat kein „Sync aus" — nur „geteilte Liste verlassen"; der Owner darf Sync erst ausschalten, wenn keine Mitglieder mehr da sind. Kick/Leave und die Owner-Sperre beim Ausschalten sind noch nicht gebaut (siehe Roadmap) — dieser PR liefert nur das Fundament (Rollenmodell + Owner-only-Teilen).

- **Server-Preset-TTLs statt freier Dauer.** Der Client schickt `"1h"`\|`"24h"`\|`"7d"`\|`"30d"`, der Server validiert dagegen und berechnet `expires_at` selbst (`entities.ParseInviteTTL`). Eine frei wählbare Dauer hätte einem Client erlaubt, `expires_at` beliebig weit nach vorn (faktisch nie ablaufend) oder in die Vergangenheit zu schieben.
- **Nur der Hash des Tokens wird persistiert** (`list_invites.token_hash`, sha256). Der Klartext existiert genau einmal — in der Create-Response — und wird danach nirgends mehr gespeichert oder zurückgegeben; „aktive Einladungen" (`GET .../invites`) zeigt nur Metadaten. Ein DB-Leak gibt damit keine nutzbaren Invite-Links her.
- **Der Link ist mehrfach nutzbar**, gültig bis Ablauf oder Widerruf — kein Verbrauch beim ersten Redeem. Passt zum Anwendungsfall „Familie/Haushalt", wo mehrere Personen über denselben Link beitreten sollen.
- **Redeem ist idempotent.** Wer bereits Mitglied ist, bekommt beim erneuten Einlösen desselben (oder eines anderen) Tokens für dieselbe Liste `already_member: true` statt eines Fehlers oder einer zweiten Mitgliedszeile — wichtig, weil ein Client eine 200-Antwort verlieren und sicher retryen können muss.
- **Claim-on-first-invite als Bootstrap für Bestandslisten.** `todo_lists` hatte vor diesem Feature kein Ownership-Modell; jede existierende Liste hat also niemanden, der sie „besitzt". Hat eine Liste noch keine Mitglieder, wird der erste Einladende automatisch `owner` (`ListMemberRepository.ClaimOwnershipIfUnowned`, atomar über `NOT EXISTS` + Insert). Danach ist Teilen (Einladen, Einladungen einsehen, widerrufen) ausschließlich Owner-Sache — ein beigetretener `member` darf nicht selbst weiter einladen; siehe die Zielarchitektur-Notiz zu Beginn dieses Abschnitts.
- **Membership-Modell existiert, wird aber (noch) nicht erzwungen.** Dieses Feature fügt `list_members`/`list_invites` und die REST-Schicht dafür hinzu — es ändert **nichts** an `/api/v1/events` oder `/api/v1/sync/*`. Jeder gültige Token darf dort weiterhin jede bekannte Listen-UUID lesen/schreiben, unabhängig von `list_members` (dieselbe, oben bereits dokumentierte User-Scoping-Lücke). Enforcement auf den Sync-Endpunkten ist bewusst ein eigener, späterer Schritt: Bestandslisten haben ohne die Claim-Logik hier keine Mitglieder, ein sofortiges Enforcement würde alle bestehenden Nutzer aussperren.
- **Der Deep-Link/URL wird im Frontend aus dem Token gebaut**, nicht vom Backend geliefert — das Backend kennt keine Frontend-Routen und soll sie nicht festlegen müssen.
